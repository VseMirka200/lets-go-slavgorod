# Участие в разработке

**Русский** | [English](CONTRIBUTING_EN.md)

Спасибо за интерес к проекту «Поехали! Славгород». Исправления ошибок, улучшения интерфейса, тесты, документация и предложения по качеству данных приветствуются.

## Перед началом

1. Проверьте, нет ли уже похожего issue или pull request.
2. Для заметного изменения сначала опишите проблему или ожидаемое поведение в issue.
3. Не публикуйте секреты, ключи подписи, персональные данные и приватные журналы приложения.
4. Потенциальные уязвимости отправляйте по инструкции из [SECURITY.md](SECURITY.md), а не в публичный issue.

## Локальная разработка

Клонируйте репозиторий и соберите debug-версию через Gradle Wrapper:

```bash
git clone https://github.com/VseMirka200/lets-go-slavgorod.git
cd lets-go-slavgorod
./gradlew assembleDebug
```

На Windows используйте `gradlew.bat` вместо `./gradlew`.

Проект использует Android Gradle Plugin и Gradle Wrapper из репозитория. Для работы выбирайте JDK, совместимый с текущими версиями Android Gradle Plugin и Gradle, и установленный Android SDK для `compileSdk 36`.

## Проверки

Перед pull request по возможности выполните:

```bash
./gradlew test
./gradlew lint
./gradlew detekt
```

Если изменение касается UI, маршрутизации или Android API, дополнительно проверьте приложение на эмуляторе или физическом устройстве.

## Стиль изменений

- придерживайтесь существующей структуры пакетов и именования;
- делайте изменения небольшими и тематически связанными;
- не смешивайте рефакторинг с функциональным изменением без необходимости;
- добавляйте или обновляйте тесты, когда меняется проверяемая логика;
- обновляйте README и другие документы, если меняется пользовательское поведение, требования или публичные настройки;
- не форматируйте несвязанные файлы только ради изменения стиля.

## Pull request

В описании pull request укажите:

- что изменено;
- зачем это нужно;
- как это было проверено;
- есть ли изменения интерфейса, расписания, разрешений или сетевого поведения;
- какие связанные issue закрываются.

Для визуальных изменений полезно приложить скриншоты до и после.

## Данные расписания

Расписание — пользовательски значимая информация. Изменения формата, источника, правил валидации или отображения времени должны сохранять понятное поведение при сетевых ошибках и некорректных данных. Не добавляйте в код приватные URL, токены или источники, которые нельзя безопасно публиковать.

## Release-сборки

Release-подпись не должна храниться в репозитории. Для локальной release-сборки используются переменные окружения `KEYSTORE_PATH`, `KEYSTORE_PASSWORD`, `KEY_ALIAS`, `KEY_PASSWORD` или поддерживаемые параметры `android.injected.signing.*`.

## Документация

Публичный сайт находится в каталоге `docs/`. Если изменение затрагивает поведение приложения, политику конфиденциальности, безопасность или пользовательские инструкции, проверьте, требуется ли синхронное обновление страниц сайта.
