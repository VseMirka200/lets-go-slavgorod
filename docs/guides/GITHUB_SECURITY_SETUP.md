# Настройка защиты GitHub для «Поехали! Славгород»

Этот документ фиксирует необходимые проверки и правила сопровождения
Android-приложения. **Не публикуйте секреты подписи APK в репозитории.**

## Проверки перед объединением PR

GitHub Actions для этого Kotlin/Android-проекта формируют следующие
проверки (точные имена `jobs.<job_id>.name`):

| Проверка | Workflow | Что проверяет |
| --- | --- | --- |
| `Tests, lint and Detekt` | `quality.yml` | Kotlin-тесты, lint, Detekt, сборка debug APK |
| `Dependency review` | `security.yml` | Новые уязвимости зависимостей в PR |
| `CodeQL` | `security.yml` | Статический анализ **Java/Kotlin**, а не Python |
| `Validate schedule data` | `validate-schedule-data.yml` | Формат и целостность данных расписания |

## Порядок включения защиты main

На 3 ноября 2026 года ветка `main` не защищена, а Ruleset для неё
отсутствует. До включения защиты необходимо загрузить исправления в
`main` и дождаться успешного CI на итоговом коммите.

Только после этого включите Pull Requests в настройках репозитория и
оставьте squash единственным разрешённым способом слияния. Создайте
активный Ruleset для `refs/heads/main` со следующими параметрами:

- запрет удаления ветки и force push;
- обязательный Pull Request;
- четыре обязательные проверки из таблицы выше;
- `Require branches to be up to date` (strict status checks);
- пустой список bypass: правила действуют также для администратора.

Для одного владельца допустимо иметь 0 обязательных одобрений, пока не
появился второй сопровождающий. Не отключайте защиту ради обхода CI.

Все три workflow запускаются на каждом PR в `main` без фильтра по путям.
`Dependency review` запускается для каждого события `pull_request`,
даже если зависимости не менялись; на push и расписании job пропускается.
Перед завершением настройки проверьте на PR наличие всех четырёх статусов.
Пропуск Dependency review на push не подтверждает успешную проверку PR.

## Защита Android-релизных тегов

Оба существующих Tag Ruleset активны и охватывают `refs/tags/*`,
включая опубликованные теги `3.0.0`, `3.0.1`, `3.0.2`:

- [protect-release-tags](https://github.com/VseMirka200/lets-go-slavgorod/rules/26457255):
  запрещены удаление, изменение и force push; bypass отсутствует.
- [restrict-release-tag-creation](https://github.com/VseMirka200/lets-go-slavgorod/rules/26457294):
  запрещено создание тегов с исключением Repository admin → Always allow.

Исключение администратора относится только к созданию тегов и не позволяет
изменять или удалять существующие теги. Сохраняйте оба правила и проверяйте
их через Rulesets API без создания пробных тегов и релизов.

## Android-подпись релизов

Android использует собственное подписание APK/AAB ключом из keystore
(`.jks`/`.keystore`), **не Windows Authenticode и не SignPath**.
Приложение уже имеет release signing config, читающий
`KEYSTORE_PATH`, `KEYSTORE_PASSWORD`, `KEY_ALIAS`,
`KEY_PASSWORD`. Ключ никогда не добавляйте в Git, переписку или
логи GitHub Actions.

Для обновлений существующего приложения нужен тот же действующий
подписывающий ключ или документированная поддерживаемая схема
ротации. Не создавайте новый keystore и не меняйте applicationId
`ru.slavgorod.transport` без отдельного плана миграции: обычное
Android-обновление может перестать устанавливаться.

Автоматического workflow публикации подписанных APK в репозитории нет. Это отдельный этап после проверки хранения ключа,
поддерживаемого `versionCode` и способа распространения APK.

## Обслуживание

Dependabot будет продолжать открывать PR по еженедельному расписанию.
Автоматическое **слияние** в настройках репозитория отключено. Обновления
следует читать и сливать вручную после тестов и dependency review.

GitHub App, подключённый к ChatGPT, может изменять файлы и
создавать PR, но не может редактировать административные Ruleset.
Для административных настроек нужен доступ владельца к Settings.
Изменение файлов само по себе не включает Pull Requests или защиту main.
